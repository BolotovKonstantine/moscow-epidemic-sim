# Прототип контракта ядра (#33)

Сравнительный прототип для выбора контракта расчётного пакета и ядра. Общие правила записи замеров описаны в [../README.md](../README.md), сам контракт — в [docs/sim-core.md](../../docs/sim-core.md). Это не код ядра и не экспорт пакета: загрузчик (#37), экспорт таблиц (#36), часы и очередь (#40) пишутся заново по контракту, с тестами.

## Что проверяется

- **Формат `.mtab` версии 1** на реальных данных. [export_tables.py](export_tables.py) переводит промежуточные файлы пакета этапа 1 в таблицы зданий, зон, узлов и дуг дорожного графа (CSR) с `index.json`. Состав колонок неполный: только для оценки размеров и чтения.
- **Чтение в память против mmap.** [proto.cpp](proto.cpp) загружает таблицы обоими способами, проверяет заголовок, колонки и SHA256, затем проходит по всем страницам. Отдельно отклоняется испорченная таблица: неверная магия, колонка за пределами файла и смещение у края u64, при котором сложение переполнилось бы.
- **SHA256.** Сравниваются системная реализация (CommonCrypto) и переносимая на чистом C++.
- **Байты на жителя.** Создаются массивы SoA предлагаемых колонок этапа 3 на всё население пакета, дом выдаётся по точным числам жителей зданий. Меряются время и прирост `phys_footprint`.
- **RNG.** Сравниваются Philox4x32-10 и хеш SplitMix64 как счётчиковые генераторы, ключ — (поток, ID, время, номер розыгрыша). Проверяется, что обход в обратном порядке даёт те же значения.
- **Очередь событий на модельные сутки всего населения:** у каждого жителя 4 события, ключ u64 = (время << 32) | ID. Сравниваются двоичная куча на векторе (пик памяти — по его ёмкости) и корзины по минуте с сортировкой корзины. Порядок (время, ID) проверяется на каждом событии, контрольные суммы обоих вариантов должны совпасть.

## Запуск

Из корня репозитория, рабочий каталог вне Git:

```sh
benchmarks/core_contract/run.sh data/packages/moscow-2021-0.5.0 build/bench/core_contract
```

Третий аргумент задаёт меньшую численность населения (по умолчанию — сумма жителей зданий пакета; больше неё прототип не принимает: дома выдаются только по жителям зданий). Мини-город для проверки на малой сцене собирается функциями `tests/city_pipeline/synthetic_city.py` и `build_package` так же, как в `tests/city_pipeline/test_build.py`, после чего `run.sh` запускается на его каталоге.

## Результаты

### 12 октября 2026, эталонный Mac

MacBook Pro 13" M1, 16 ГБ, macOS 26.5.1, от сети. Seed и потоки зашиты в `proto.cpp`: население — seed 20261012, поток 1; замер RNG — ключ `stream_key(1, 2)`; очередь — `stream_key(7, 3)`. При других значениях распределение событий по корзинам, а с ним время и пик, будут другими. Код прототипа — как в коммите `3079ad6`: прогон сделан на рабочем дереве, совпадавшем с ним по `proto.cpp`, `export_tables.py` и `run.sh`, а до `e254c71` эти файлы не менялись. `clang++ -O2`, один поток. Пакет `moscow-2021` 0.5.0. Кеш файлов ОС тёплый: экспорт только что записал таблицы. Холодное чтение с диска не мерялось, сброс кеша требует прав администратора.

**Таблицы:** 575 438 зданий, 7983 зоны, 406 048 узлов, 1 019 340 дуг. Всего 59,5 МБ: здания — 27,6, дуги — 20,4, узлы вместе со смещениями CSR — 11,4, зоны — 0,1. Экспорт на Python занял 9,4 с.

| Загрузка всех таблиц | Время |
| --- | --- |
| Чтение в память + SHA256 CommonCrypto + проверка заголовков | 52 / 38 / 31 мс (прогоны 1–3) |
| То же, переносимый SHA256 | 282 мс |
| mmap + проверка заголовков, без SHA256 | ~1 мс + 5 мс на первый проход по страницам |
| mmap + SHA256 CommonCrypto | 28 мс |
| Полный проход по загруженным таблицам | 1–3 мс |

Испорченная таблица отклоняется: `corrupt_rejected = true`.

**Население:** 17 284 969 жителей (совпадает с суммой жителей зданий пакета), 36 байт на жителя, массивы SoA — 622 МБ, прирост footprint — 606 МБ. Генерация служебных полей заняла 0,55–0,75 с; реальные профили и семьи — задача #38.

**RNG:** 138,3 млн розыгрышей. Philox4x32-10 — 7,9–8,4 нс на розыгрыш, SplitMix64-хеш — 1,15 нс (скалярный код без векторизации). Порядок обхода на результат не влияет.

**Очередь на сутки (69 139 876 событий):**

| Вариант | Время | Пик памяти очереди |
| --- | --- | --- |
| Двоичная куча на векторе (`std::push_heap`) | 41,4 / 42,7 с | 286 МБ (по ёмкости вектора) |
| Корзины по минуте на 48 ч + сортировка корзины | 3,8 / 3,8 с | 270 МБ (суммарная ёмкость векторов, включая обрабатываемую корзину; пересчитано при каждом росте) |

Обе очереди дали одинаковую последовательность (`queues_agree = true`). Пик корзин сначала снимался раз в модельный час и составил 269 МБ. Точный учёт при каждом росте ёмкости даёт 270,2 МБ; время того прогона искажено нагрузкой системы и не приводится. Замерено только кольцо минутных корзин: события укладываются в 30 часов, устаревших ключей нет. Суточные корзины за горизонтом и сжатие устаревших ключей из [sim-core.md](../../docs/sim-core.md#время-и-очередь-событий) прототип не реализует, их замер — #40. Время двух прогонов разделено «/». Во время включены и розыгрыши Philox: по одному на событие, 69,1 млн, около 0,55 с.

**Контрольный прогон под нагрузкой** с чистого коммита `e254c71`: средняя загрузка системы 58, работали виртуальная машина и браузеры. Корзины — 14,6 / 6,1 / 6,5 с, куча — 56 / 133 / 65 с, Philox — 9,4–16,6 нс. Абсолютные числа под нагрузкой не годятся, но разрыв между кучей и корзинами (в 4–20 раз) сохраняется. Чистый повторный прогон на ненагруженной машине стоит сделать при review.

**Мини-город** (синтетический пакет тестов, 1671 житель): загрузка, отклонение порчи, точное число жителей и совпадение очередей подтверждены. Повторный экспорт даёт те же SHA256.

## Выводы для контракта

- Чтение 60 МБ в память с полной проверкой SHA256 занимает десятки миллисекунд, а в масштабе всей загрузки mmap почти ничего не выигрывает. Выбор автора (чтение в память) подтверждён. SHA256 проверяется при каждой загрузке. Ядру нужна аппаратно ускоренная реализация: переносимый C++ в 8–9 раз медленнее.
- Куча не годится для цели «сутки за 5–15 с»: только очередь занимает ~40 с, а памяти куча берёт не меньше корзин. Нужна календарная очередь с минутными корзинами, ключ (время, ID) в одном u64.
- Philox4x32-10 укладывается в бюджет: ~1 с на 138 млн розыгрышей, а за сутки их нужно порядка числа событий. Он выбран основным генератором, потому что проверен статистически (BigCrush в Random123). SplitMix64-хеш быстрее, но слабее как ключевая функция.
- 36 байт на жителя дают 0,62 ГБ на всё население. С таблицами, очередью и резервом под болезнь получается около 1,1 ГБ без кеша маршрутов (см. бюджет в [docs/sim-core.md](../../docs/sim-core.md#бюджет-памяти)).
