# Замер просмотра карты (#17)

Протокол замера карты всего региона для этапа 2. Общие правила записи — в [../README.md](../README.md).

## Запуск

```sh
benchmarks/map_view/run.sh                       # экспорт release и два прогона в развёрнутом окне
WINDOW=1600x1000 benchmarks/map_view/run.sh      # окно в физических пикселях
NO_EXPORT=1 RUNS=3 benchmarks/map_view/run.sh    # без повторного экспорта, три прогона
```

Нужны шаблоны экспорта Godot 4.7.2, release-библиотека ядра (`scons platform=macos target=template_release`, см. [native/AGENTS.md](../../native/AGENTS.md)) и пакет с картой в `data/packages/` (или `MAP_DIR=<каталог map>`). Скрипт экспортирует `build/exports/macos-release/MoscowEpidemicSim.app`, запускает его с `--bench-map=route.json` под `/usr/bin/time -l` и пишет в `build/bench/map_view/<время UTC>/` (вне Git) `run-<n>.json`, журнал и вывод `time`, а также сводку `summary.md` и `summary.json` с устройством, питанием, коммитом и версией пакета. Прогон длится около полутора минут, окно игры открывается на экране; компьютер в это время лучше не трогать.

## Что меряется

Маршрут — [route.json](route.json) (формат `mesim-map-bench` 1): точки в EPSG:32637, масштаб — метров на пиксель вида карты. Вид — 1280×720 и растягивается на окно, поэтому видимая область не зависит от размера окна, а размер окна меняет только число пикселей отрисовки.

| Сценарий | Вид |
| --- | --- |
| `overview` | Весь регион в окне, слои по умолчанию (дороги, граница) |
| `overview_layers` | То же, плюс население по зонам, транспорт, учреждения, сетка зон |
| `center_close` | Китай-город, 1 м/пикс. (подробность 2), слои по умолчанию |
| `center_close_layers` | То же, плюс функции зданий, транспорт, учреждения, сетка зон |
| `flight` | 62 с: с общего вида к Кремлю, вблизи (1,5 м/пикс.) к Белорусской и Курской, к Москва-Сити, отдаление до 12 м/пикс., через полрегиона к Зеленограду, снова весь регион |

Режим замера (`MapBench`, [game/scripts/bench/map_bench.gd](../../game/scripts/bench/map_bench.gd)) выключает вертикальную синхронизацию и предел FPS, разворачивает окно (или задаёт размер), ждёт 1,5 с, затем по каждому сценарию: для неподвижного вида сразу догружает нужные участки, 120 кадров прогрева и 1200 кадров замера; облёт начинается с общего вида, участки грузятся как в игре — в фоне. Метрики:

- **Время кадра** — между соседними кадрами основного цикла (с выключенным vsync — стоимость кадра, а не частота экрана): среднее, 50/95/99-й перцентили, максимум, число кадров дольше 16,7 мс (меньше 60 FPS).
- **Отрисовка (CPU)** — `viewport_get_measured_render_time_cpu`; время GPU в Compatibility не измеряется (в результате `null`).
- **Подгрузка** — кадры, когда часть нужных участков ещё не подключена (вместо них видна грубая геометрия); число подключённых участков; время подключения в основном потоке за кадр; время чтения и подготовки участка в рабочем потоке (до четырёх параллельно).
- **Память** — пик кеша участков (оценка `MapTileView.data_bytes`), видеопамять Godot, у процесса — максимальный RSS и пик footprint из `/usr/bin/time -l`; статическая память Godot считается только в debug-сборке.
- **Диск** — размер участков по уровням из индекса пакета.

**Сравнение с целью 60 FPS (16,7 мс на кадр)** — только для этого устройства, сборки и пакета, без обобщения на другие компьютеры:

- В окне 1600×1000 цель выполнена во всех сценариях по среднему и 95-му перцентилю (неподвижный вид — 6–7 мс, облёт — 14 мс); дольше 16,7 мс — до 1,5 % кадров облёта и единичные кадры неподвижного вида.
- В развёрнутом окне (2880×1556) неподвижный вид в среднем укладывается в цель (7–11 мс), но 95-й перцентиль со слоями — 15–18 мс, дольше 16,7 мс — до 10 % кадров. Облёт в среднем укладывается (12 мс, 82 FPS), 95-й перцентиль — 18–19 мс, дольше 16,7 мс — 12,5 % кадров: цель по 95-му перцентилю **не выполнена**.
- Разница между окнами при почти одинаковой отрисовке на CPU (95 % — 1–3 мс) указывает, что неподвижный вид упирается в GPU (число пикселей). Облёт и в малом окне вдвое дороже неподвижного вида — дополнительная работа основного потока при движении камеры (раскладка подписей, выбор участков, подключение); это предположение по косвенным данным, профилирование не проводилось.

Расхождение прогонов: в окне 1600×1000 — до 0,1 мс по среднему и 0,2 мс по 95-му перцентилю; в развёрнутом окне — до 2,6 мс по среднему и 6,3 мс по 95-му перцентилю (сильнее всего — первые сценарии прогона 1 и `center_close` прогона 2). Замер сделан от батареи; повтор от сети не проводился.
