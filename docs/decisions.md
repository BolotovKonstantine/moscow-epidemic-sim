## Реализация этапа 1

Предложения, принятые в первом городском пакете `moscow-2021` 0.1.0; их можно пересмотреть после проверки:

| Решение | Обоснование |
| --- | --- |
| Метрическая проекция `EPSG:32637` (UTM 37N) | Стандартная проекция для долготы Москвы; искажение масштаба на территории региона мало для буферов и площадей |
| Зоны — квадраты 1 км в этой проекции, обрезанные границей | Стабильные ID, не зависят от административных границ, достаточно мелкие для кордонов; размер — параметр |
| Потолок плотности 0,1 жителя на м² площади этажей | Ограничивает скопление населения сетки в немногих зданиях; избыток уходит соседним зданиям без функции и в блок 5×5 зон |
| Здания без функции получают население только как запасной вариант | Большое здание без тега не объявляется жилым; метод распределения сохраняется по зданию |
| Промежуточные форматы — CSV и GeoJSON по строкам в gzip | Простая проверка и воспроизводимые байты; бинарные участки для Godot — на этапе 2 |
| МКАД ищется по `ref`/`loc_ref` = `МКАД`, внешний край — 15 м от осей проезжих частей | В OSM-2021 МКАД размечен через `loc_ref`; площадь внутри проверяется (850–900 км²) |
| Неоднозначные теги не считаются наблюдением | `building:levels` принимается только одним числом, `height` — в метрах или футах; иначе этажность оценивается с `levels_source=default` |
| Вырезка OSM дополняет маршруты всеми членами | Остановки за границей известны с координатами; выход маршрута из региона определяется по ним, а не по пропавшим членам |
| Учреждение из точки, корпуса и территории — одна запись | Дубли объектов OSM одного вида объединяются по самому большому контуру, исходные ID сохраняются |

## Вопросы для следующих шагов

Они не мешают подготовке плана, но должны быть решены перед зависимой реализацией.

- Какая модель ПК (Windows x86_64) и какой iPhone будут эталонными устройствами? Mac выбран; ПК и iPhone решаются позже, замеры этапа 0 — только на Mac.
- На какой сезон рассчитан первый сценарий и какая продолжительность партии удобна? Срез данных — около 2020–2021.
- Нужна ли полная автономность сразу после установки или допустима отдельная загрузка городского пакета?
- Какой ожидается вид: аналитическая городская карта или более выраженная стилизация игры?
- Сколько времени в неделю автор планирует уделять проекту и какие языки уже знает?
- Какую глубину журналирования хранить для обычных жителей? Индивидуальные состояния обязательны; полные журналы всех поездок требуют отдельного бюджета памяти.

## Основные риски и решение на старте

| Риск | Действие |
| --- | --- |
| Потоки и мощности учреждений недоступны | Разделять наблюдаемые данные, оценки и игровые настройки; использовать воспроизводимые заменители |
| Полный регион не помещается на телефоне | Ранний замер, загрузка геометрии по участкам, компактные массивы агентов и профиль затрат |
| Оптимизация контактов меняет вероятность | Индивидуальный эталон, проверка распределений и устойчивых домашних связей |
| События и журналы занимают больше памяти, чем профили | Ограничить временные буферы, разделять текущие состояния и подробную историю |
| Карта выглядит убедительно при слабой модели | Отдельно проверять городскую динамику и цепочку последствий решений |
| Работа растягивается из-за числа систем | Полный регион с малым числом механик, завершённая партия до новых подсистем |

Крупнейшая неопределённость — достигнет ли индивидуальная модель всего региона нужной скорости и точности на iPhone при полном регионе. Она проверяется прототипом; текущий план не означает, что этот технический вопрос уже решён.
