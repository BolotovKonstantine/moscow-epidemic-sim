## Предложения по реализации

| Решение | Обоснование | Когда проверить |
| --- | --- | --- |
| Двухмерная карта | Хорошо читается на компьютере и телефоне | Первый просмотр карты |
| Индивидуальные агенты в компактных массивах | Соответствует требованию профиля каждого человека | Ранний замер всей численности региона |
| Целочисленные случайные заражения | Сохраняют смысл одного пациента и раннее затухание | Малые математические сцены |
| C++ ядро через GDExtension, GDScript для интерфейса | Масштаб миллионов индивидуальных жителей | Пробные сборки и замер до игровых механик |
| Python для подготовки геоданных | Отделение сложной обработки от игрового приложения | Сборка городского пакета |
| Сценарий работает локально после установки данных | Не требует городских API во время партии | Проверка без сети |
| Маски, удалённая работа и кордон в MVP | Проверяют риск, движение и изменение графа | Игровой сквозной сценарий |
| Простые автоматические противники | Позволяют играть за обе стороны без мультиплеера | Первые завершённые партии |
| ПК предварительно означает Windows | Нужен конкретный экспорт и эталон | До настройки сборок |
| Полное население и точные реальные потоки различаются | Численность можно ограничить статистикой, спрос часто нужно оценить | Проверка источников и калибровка |

## Реализованная техническая основа

6 октября 2026 года добавлен [паспорт городского пакета версии 1](city-package.md): JSON Schema, CLI проверки метаданных и SHA256, синтетический пример и тесты. Это технический формат первого прототипа, а не новое подтверждённое решение автора о содержимом города. Год сценария, метрическая проекция реального региона и форматы больших таблиц остаются открытыми.

## Вопросы для следующих шагов

Они не мешают подготовке плана, но должны быть решены перед зависимой реализацией.

- Какая модель ПК (Windows x86_64) и какой iPhone будут эталонными устройствами? Mac выбран; ПК и iPhone решаются позже, замеры этапа 0 — только на Mac.
- На какой год или сезон рассчитан первый сценарий и какая продолжительность партии удобна?
- Нужна ли полная автономность сразу после установки или допустима отдельная загрузка городского пакета?
- Какой ожидается вид: аналитическая городская карта или более выраженная стилизация игры?
- Сколько времени в неделю автор планирует уделять проекту и какие языки уже знает?
- Какую глубину журналирования хранить для обычных жителей? Индивидуальные состояния обязательны; полные журналы всех поездок требуют отдельного бюджета памяти.
- Достаточно ли модельных транспортных потоков, ограниченных доступной статистикой, если открытые реальные матрицы получить не удастся?

## Основные риски и решение на старте

| Риск | Действие |
| --- | --- |
| Потоки и мощности учреждений недоступны | Разделять наблюдаемые данные, оценки и игровые настройки; использовать воспроизводимые заменители |
| Полный регион не помещается на телефоне | Ранний замер, загрузка геометрии по участкам, компактные массивы агентов и профиль затрат |
| Оптимизация контактов меняет вероятность | Индивидуальный эталон, проверка распределений и устойчивых домашних связей |
| События и журналы занимают больше памяти, чем профили | Ограничить временные буферы, разделять текущие состояния и подробную историю |
| Карта выглядит убедительно при слабой модели | Отдельно проверять городскую динамику и цепочку последствий решений |
| Работа растягивается из-за числа систем | Полный регион с малым числом механик, завершённая партия до новых подсистем |

Крупнейшая неопределённость — достигнет ли индивидуальная модель всего региона нужной скорости и точности на iPhone при полном регионе. Она проверяется прототипом; текущий план не означает, что этот технический вопрос уже решён.
