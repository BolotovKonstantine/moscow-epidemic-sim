# Ведение проекта

Проект ведётся через [GitHub Issues](https://github.com/BolotovKonstantine/moscow-epidemic-sim/issues), [Project](https://github.com/users/BolotovKonstantine/projects/7) и pull requests. Этот документ задаёт рабочий процесс для автора, участников и ИИ-ассистентов. Архитектура остаётся в [architecture.md](architecture.md), объём этапов — в [roadmap.md](roadmap.md), подтверждённые решения — в [decisions.md](decisions.md).

## Где хранится информация

| Место | Назначение |
| --- | --- |
| `docs/roadmap.md` | Этапы 0–8 и критерии их завершения |
| Карточки этапов в Project, вид «Этапы 0–8» | Обзор последовательности; ссылки на задачи этапа |
| Milestones репозитория | Этап каждой рабочей Issue и прогресс включённых задач |
| Issue репозитория | Конкретная задача, ошибка, источник данных или обсуждение решения |
| Project Status | Текущее состояние исполнения задачи |
| Pull request | Реализация, проверка и связь с Issue |
| `docs/decisions.md` | Принятые автором решения и открытые вопросы со ссылками на обсуждения |
| `AGENTS.md` модулей | Воспроизводимые команды сборки, запуска и тестов |
| `benchmarks/` | Протоколы замеров с окружением и параметрами |

Существующие девять карточек этапов — DraftIssue для обзора. Работу ведём в обычных Issues репозитория, добавленных в Project. Карточка этапа не заменяет задачу. В [milestones репозитория](https://github.com/BolotovKonstantine/moscow-epidemic-sim/milestones) созданы этапы 0–8 с критериями из roadmap. Для рабочей Issue автор назначает milestone того же этапа, который указан в форме. Для общей задачи этап определяется при разборе. Даты не задаются без решения автора. Этап 0 закрыт на основании roadmap. Пустая milestone не является доказательством завершения этапа.

Доска «Доска» группирует карточки по Status: `Todo`, `In Progress`, `In Review`, `Done`. На карточках отображаются исполнитель, milestone и связанный PR, если они заполнены. Вид «Этапы 0–8» показывает существующие карточки этапов по фильтру `is:draft`; рабочие задачи создавай как Issues репозитория, чтобы они не попадали в этот обзор.

## Требования к Issue

Используй форму в `.github/ISSUE_TEMPLATE/`. Заголовок описывает результат: «Построить контур региона из OSM», «Исправить проверку SHA256 на Windows». Одна задача должна давать результат, который можно отдельно проверить и включить в main. Если нужны независимые изменения разных систем, разбей работу на связанные Issues; общая Issue содержит список задач.

Перед началом реализации в Issue должны быть:

- цель и причина: какую проблему решаем;
- этап и затронутые модули;
- границы работы: что входит и что отложено;
- критерии приёмки с наблюдаемым результатом;
- способ проверки: команды, сценарий, набор данных или ручная проверка;
- зависимости и открытые вопросы; если их нет — явно «нет».

Для ошибки нужны воспроизведение, ожидаемый и фактический результат, версия/commit и окружение. Seed и версия пакета обязательны, если ошибка относится к симуляции или данным; иначе укажи «не применимо». При редкой ошибке приложи доступные свидетельства и частоту вместо выдуманного воспроизведения.

Для данных нужны URL, владелец, даты, покрытие, формат и условия использования. Неизвестная лицензия означает вопрос для исследования, а не разрешение распространять данные. Разделяй наблюдаемые значения, оценки и игровые настройки. Оценки требуют метода и неопределённости. Issue не заменяет карточку происхождения в пакете.

Для новой механики или существенного изменения архитектуры сначала создай обсуждение решения: проблема, варианты, последствия для модели/памяти/платформ и способ проверить выбор. До реализации нужно явное решение автора в Issue. Затем итог переносится в `docs/decisions.md` со ссылкой; отложенные механики не становятся разрешёнными только из-за появления Issue.

Для опечатки, сломанной ссылки и другого небольшого изменения документации отдельная Issue необязательна: причина и проверка помещаются в PR. Автоматические PR Dependabot также не требуют отдельной Issue; решение о смене Godot/godot-cpp остаётся за автором.

## Подготовка и исполнение задачи

Задача готова к работе, когда критерии понятны, зависимости доступны и решения, от которых зависит реализация, получены. Незаполненная форма и неразрешённый вопрос не являются согласованием. После разбора автор назначает исполнителя, milestone и добавляет Issue в Project; приоритет задаётся порядком карточек, без обязательной отдельной шкалы.

| Status в Project | Что означает |
| --- | --- |
| `Todo` | Задача ожидает разбора или готова, но исполнение ещё не началось |
| `In Progress` | Исполнитель работает над реализацией или исправляет замечания; draft PR остаётся здесь |
| `In Review` | Готовый PR или итог исследования передан на проверку; ожидается решение автора или слияние |
| `Done` | Автор принял результат, критерии выполнены; реализация слита, Issue закрыта |

### Критерии перемещения карточек задач

| Переход | Условия |
| --- | --- |
| `Todo` → `In Progress` | В Issue определены цель, границы, критерии приёмки и способ проверки; выбран исполнитель и milestone; блокирующие зависимости сняты, необходимые решения автора получены; исполнитель фактически начал работу |
| `In Progress` → `In Review` | Все критерии задачи подтверждены; связанный PR открыт и не draft; описание содержит результаты проверки и ограничения; документы обновлены; обязательный CI прошёл на последнем commit; выполнены применимые ручные проверки из раздела «Перед review». Для исследования без PR опубликован полный итог с доказательствами и явным запросом решения автора |
| `In Review` → `In Progress` | Получены замечания, требующие изменений, обнаружен провал проверки или невыполненный критерий; исполнитель возвращает карточку и фиксирует необходимую доработку. Повторное review — после исправления и повторной проверки изменённого результата |
| `In Review` → `Done` | Автор принял результат; все критерии выполнены или явно пересогласованы; все PR, необходимые для задачи, слиты в main; Issue закрыта как выполненная. Для исследования — автор принял опубликованный итог, нужные документы обновлены и Issue закрыта |
| `In Progress` → `Todo` | Работа приостановлена и больше не исполняется: указаны причина, оставшаяся работа и условия возобновления; задача снова ожидает назначения/старта |

Открытие PR само по себе не переводит задачу в `In Review`. Draft, частичная реализация и незавершённые проверки остаются в `In Progress`. Новые изменения в PR требуют повторной проверки готовности: если критерии или проверки ещё не подтверждены, карточка возвращается в `In Progress`. Ожидание ответа проверяющего или слияния без необходимости доработки оставляет карточку в `In Review`.

Исполнитель обновляет карточку при начале работы и передаче на проверку; автор подтверждает завершение. Переходы выполняются вручную. Ссылки на PR, результаты проверок и причины возврата фиксируются в Issue/PR, без повторного копирования всего описания. Закрытая Issue с причиной «дубликат», «отклонено» или «отменено» не считается выполненной: её карточка архивируется с сохранением причины, а не переводится в `Done`.

Эти условия относятся к рабочим задачам. Карточки этапов завершаются по отдельным критериям roadmap и разделу «Завершение и релизы», а не по наличию одного готового PR.

Не начинать много задач одновременно: у одного исполнителя обычно одна основная задача. Блокировку фиксируем в Issue: что мешает, ссылка на зависимость и какое действие разблокирует. Блокировка доработки оставляет задачу в `In Progress`; если нужна только проверка готового результата — в `In Review`; отдельный статус блокировки пока не вводим. При возобновлении обновляем запись о блокировке.

При изменении объёма обнови критерии Issue до реализации расширения. Существенное расширение требует решения автора. Для каждого критерия в итоге должна быть ссылка на PR, тест, отчёт или объяснение, почему он снят автором.

## Ветка и pull request

Ветка: `<тип>/<кратко>`, например `data/region-boundary` или `fix/manifest-paths`. Один PR решает одну связанную задачу. Для внешнего вклада используй fork; при наличии разрешения на запись — отдельную ветку репозитория. Коммитить и пушить ИИ-ассистент может только по просьбе автора. Сообщения коммитов — на русском, в повелительном наклонении.

Описание PR составляется по `.github/PULL_REQUEST_TEMPLATE.md`: проблема, изменение, связь с Issue, подтверждение критериев, проверка и ограничения. `Closes #N` используется только при полном решении Issue; для частичного результата — `Refs #N`, а оставшаяся работа перечисляется явно. Открытый draft PR позволяет показать незавершённую работу, но не означает готовность задачи.

Перед review:

- выполнены критерии Issue и обновлены документы, описывающие изменённое поведение;
- для изменённых механизмов есть соответствующие проверки; для документации достаточно проверки ссылок и согласованности;
- автоматические проверки CI проходят на последнем commit;
- при изменении C++ или моста выполнены сборка и smoke; для изменений native/game, затрагивающих экспорт, выполнена релевантная ручная проверка;
- результат ручной проверки содержит commit, команду, устройство/платформу и итог; при необходимости версия пакета и seed;
- сгенерированные бинарники, большие данные и секреты не входят в diff.

macOS CI и CodeQL C++ запускаются вручную согласно [.github/AGENTS.md](../.github/AGENTS.md). Их пропуск на обычном PR не означает успешную проверку C++. При изменениях C++ приложи результат ручного CodeQL или явно укажи его отсутствие для решения автора. Review ИИ помогает разбору, но не заменяет проверку критериев и решение владельца.

## Завершение и релизы

Только автор сливает изменения в `main` и выпускает релизы. У него сохранено исключение из правил защиты ветки; рабочий стандарт — проверять критерии и CI перед слиянием. Закрыть Issue и поставить `Done` можно после слияния реализации. Для задач без кода нужен итог с доказательствами; отклонённые и дублирующие Issues закрываются с причиной и не отмечаются как выполненная работа этапа.

Этап готов, когда выполнены его критерии из roadmap, закрыты обязательные задачи, а перенесённые пункты явно перечислены с причиной и следующим этапом. Слияние одного PR не завершает этап автоматически. Обнови roadmap и карточку этапа, закрой milestone после проверки автором. Отклонённые задачи не заменяют критерии завершения.

Релиз не требуется для каждого PR. Автор выбирает версию; описание релиза перечисляет включённые изменения, известные ограничения, совместимость пакета/сохранений и проверенные платформы. Новые результаты скорости публикуются только с воспроизводимым протоколом замера.

## Поддержание порядка

Перед новой задачей проверь существующие Issues. При завершении работы обновляй связанную Issue и статус Project; формы не добавляют карточки и не меняют статусы автоматически. Перед переходом к следующему этапу разбираем открытые задачи, зависимости и PR обновлений. Документирование процесса не требует отдельного бота, дополнительных Actions или календарного расписания.

GitHub формы проверяют заполненность обязательных полей в веб-интерфейсе. Содержание критериев и согласование проверяет автор; Issues через CLI/API и описания PR требуют того же стандарта, но шаблон технически не блокирует их создание.
